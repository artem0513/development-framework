# Managed task workflow

Use only in a project or workspace that explicitly adopted DevelopmentFramework. Pick the profile from the actual action: a financial report with warnings is a document or research task, a fix to its generator is software. Ordinary questions get their domain workflow, not a managed task.

## Before you decide

- Read task-intake for a new assignment and task-discovery before proposing implementation. Searching the project for existing examples is the default; a user opt-out skips example search and reuse (including cached/delegated examples) but not target/dependency inspection. Restore an existing task with `ase --project PROJECT restore TASK` instead of replacing it.
- Separate retrievable facts from owner-only decisions. Check supplied context, fresh memory, code, history and [answer investigation](../task-discovery/references/answer-investigation.md) first; a detail missing from the prompt is not a blocker. Ask only when checks cannot close a material gap or the owner alone must choose, and give the checked facts plus a recommendation.
- For comparisons, blockers, dependencies, actionable artifacts, semantic changes or disputed findings apply [evidence decisions](references/evidence-decisions.md): confirm target/reference authority and current artifact version, and prove findings through the real callee before repair.

A clear assignment authorizes investigation at once; work that changes code, tests, data, configuration or infrastructure starts only after the owner approves the implementation plan (see Plan and approval). Other work, such as a document or research, proceeds within scope. Before choosing or recommending a software or infrastructure solution (including fix options in a read-only investigation, an interim "quick fix" and a delegated brief), apply these rules; [proportionate solution design](references/solution-design.md) has the details and [calibration examples](references/solution-calibration.md):

- **Analyse first, code second.** For a bug, identify the actor or caller, triggering operation, scope of the rule, observed result and agreed expected outcome. Trace that exact path and identify where it first diverges. A passing run on an adjacent flow cannot establish the fix. If the expected outcome is a product decision, show the observed behavior and the unresolved choice to the owner. If you cannot reproduce the symptom or inspect the suspected source, report the missing evidence and keep the cause a hypothesis.
- **Smallest change in the project's existing patterns.** Inspect the class that already owns the behavior, its related callers and a maintained local example before adding or moving nontrivial logic. An explicit example-search opt-out still leaves the owner, callers and actual dependencies to inspect. Reuse the existing behavior when it fits and name the chosen location and reason in the technical plan. Match the project's conventions in the changed code. Fix only the behavior in scope and keep related refactoring tied to that flow. Only a risk required by the ticket, acceptance criteria or a documented contract, or a concrete counterexample showing that this change breaks an existing invariant or duplicates an external effect, justifies additional mechanisms such as locks, transactions, retries, waits, queues, caches, polling, jobs, global UI or new IDs or migrations. Record other material risks under "Not handled".
- **Domain values go through the project's helpers.** Before writing, in production code, a conversion of a domain value (date or code formats, units, encodings, numbers or keys of an external system) or a literal that stands for such a rule (a magic number, a custom format string), search the repository for the literal, the format and the domain name. Each gets one decision, named in your report: use the existing helper or constant; add a method or named constant to the existing helper class of that domain; otherwise a named constant with a one-line reason. Never inline it, and never twice. Test data, identity values, protocol status codes and standard library formats are exempt. Self-checks, lead passes and cleanup passes sweep every new conversion and magic value, not only the issues already named; "does it duplicate an existing helper" alone misses a conversion no helper has yet.
- **Integration changes.** Before adding a boundary mapping, check the producer and consumer contract. Compare maintained examples using that contract unless the owner opted out of example search. Use the established representation or raise a material conflict before inventing a translation. When removing an integration, search for its identifiers in source, configuration, deployment and docs, and remove obsolete references within scope. See [solution design](references/solution-design.md#4-fix-at-the-source-for-every-consumer).
- **Fix at the source, everywhere it occurs.** Verify the first point where the value becomes wrong and fix the responsible component. Check its handling of the same condition on sibling paths and identify affected consumers. A compatible correction within approved scope proceeds. When the correction has broad downstream impact or there is a credible risk that consumers rely on the wrong behavior, show the evidence and get the owner's decision before editing the affected flow. If the source is protected, request `ase authorize-protected` and wait for that decision. If another team owns it, recommend the source fix and use its own review or child task. A consumer-side workaround for a source fault requires a documented requirement or contract, or explicit owner approval when the source cannot be changed. For a temporary workaround name the upstream fix and when the workaround can be removed. Include the same fault at its in-scope entry points and follow [out-of-scope discovery](#out-of-scope-discovery) for other defects.
- **Ambiguous upstream data.** For a workaround that affects a charge, permission or stored record, show how to distinguish a bad response from a valid one. If the evidence cannot distinguish them and there is no authorized fallback, hold the dependent edits and ask the owner to decide.
- **Your call, no question:** code in any service of this repository or workspace checkout, new files/folders and library or test projects (including a minimal test project), an index or constraint migration a requirement needs (table/column changes need owner approval), additions that follow a pattern the service already uses (another repository, service, mapper profile, or Unit of Work where one exists), and refactoring whose risk you judge low or medium in the task's code or the flows the task tests. A separate Git repository changes through its own child task with its own finish and PR; link the PRs and say the dependency PR must merge first. Write the tests; a test plan is not a test.
- **Owner approval before you build** (the canonical infrastructure list): adding or removing a table or a column, a database, a separately deployed service/app, a serverless function (e.g. Azure Function), a timer or background job (including in-process timers and hosted jobs), a queue/topic/subscription, an external provider or platform, or a cloud resource; replacing a technology (message broker, database engine); a DB function/procedure/trigger unless the project already uses them for that logic. An externally consumed message type on an existing queue still changes a cross-service contract. Send the need, evidence, options from simplest up and a recommendation.
- **Do not hold a ready change** for facts you can retrieve, another team's review or release timing. When the ticket implies a date ("next month"), state it in the release note and proceed.
- **Answer with the fact.** When the owner asks what something is or whether something exists (a helper, a constant, a caller, a pattern), run the read-only search first and answer with the result and a proposal; "I need to check" or "we could look for a helper" is not an answer.
- **One ticket per PR**, no incidental shared-code or unrelated changes; a short, plain PR description. The ticket key goes into branch names, commits and PR descriptions only for that ticket's work; a defect outside it gets no key, branch or PR until the owner opens its task.

## Out-of-scope discovery

In scope are the root cause of the ticket's own defect or requirement (also in shared code), the same fault at that defect's other entry points, and a fault in the behaviour this change itself modifies; out of scope is a pre-existing defect that is only observed, or that only blocks a check whose goal is already shown. A pre-existing defect elsewhere that prevents a criterion is a blocker and an owner question, never in scope by itself.

An out-of-scope defect found during the work (outside the in-scope list above: not described by the ticket or its acceptance criteria and not caused by this task's changes) is reported, not fixed: no fix, commit, branch or PR for it, neither in the current PR nor in a separate one. Report it as one line: "Found separate defect X (evidence); outside this ticket, left untouched. Open a separate task?" The question is whether it is needed at all; never offer a choice of where to put the fix ("this PR or a separate one?"). Only the owner's explicit permission for that specific defect lifts this; "your call", routine fixes, useful alternatives, in-scope choices, owner pre-approval of recommendations, or a plan item the agent itself recommended never cover it. A permitted fix gets its own task, ticket key and PR unless the owner explicitly says to include it in the current PR.

If such a defect blocks verifying a criterion, judge the criterion's goal, not its literal form, but only when all of these hold: (a) the criterion is a denial or other negative goal; a positive criterion ("editors can export") is never met by a 401; (b) the observed outcome is a deliberate denial by a working control on that request (a 4xx authentication or authorization refusal, no data returned), never a 5xx, timeout, crash or empty 200; (c) executed evidence still exercises the task's own changed code path, for example a test with a directly built or stubbed principal; (d) the literal form is not itself the requirement (for example a documented status-code contract). Then the criterion is met with a note naming the defect: a download refused at authentication (401 where 403 was written) still meets "this client cannot download the file". Without (c) it is unverified, missing coverage you close with that test, not met. If (a), (b) or (d) fails, it is a blocker and an owner question, not a fix.

## Plan and approval

- **Implementation plan before any change** to code, tests, data, configuration or infrastructure. First investigate with read-only actions only: code and how the project already does this, Git history, requirements and business context, the whole call chain across services, databases and transports, and where the flow continues after the changed point (who consumes the result, which other scenarios it affects). Reading, running existing tests and reproducing the problem without writes to shared data are allowed; editing code, tests, data or infrastructure waits for approval.
- **Resolve failure behavior before choosing the patch.** When the change can leave a committed write or external effect followed by an error, trace what the caller sees, what persists and what a retry does. A similar pattern elsewhere does not settle whether that outcome is acceptable here. If the existing contract or approved plan settles it, proceed within scope. Otherwise show the concrete outcome and options to the owner and hold the edits that depend on the answer.
- For a scheduled job, verify actual deployment and retry behavior before claiming single execution. State any missing facts as conditions on the recommendation.
- Give the owner a short plan in plain language with the expected behavior, the existing path you inspected, the proposed change and how you will verify it. Identify the exact code location in the technical plan. If an approved clarification narrows or changes the ticket, cite it and state the remaining obligation and its owner. Include the three decision levels, each stated even when empty ("HIGH: none").
  - **HIGH** - infrastructure: any item in "Owner approval before you build" above.
  - **MEDIUM** - a new direct third-party dependency or a new direct dependency on a shared library, a material application architecture change (such as a new layer or the first Unit of Work), or a material change to shared behavior or a cross-service contract. Apply the same rule in every affected service. Ordinary use of a pattern established in the target service stays autonomous within the approved plan.
  - **LOW** - risky or complex refactoring required by the task. Report a worthwhile refactoring outside the task's flows separately for the owner to consider.
  - For each item: options from the simplest (keep the current way, do nothing; a workaround at the wrong place is not simpler), each with a 0-100 score and two or three short reasons; your recommendation, your confidence and what would change it.
- Keep the full plan (files, options, test scenarios) in the proposal and its notes. Name each material decision, its requirement, the existing alternative and why it falls short, and the affected services or resources. A reply approving the plan after the owner sees it covers the choices it names. Record it with `ase task approve TASK --proposal-hash <hash from propose/status> --user-message-ref <that reply>`. If a material in-scope decision emerges later, show it to the owner and get approval for that change before editing the affected part.
- **Pre-approval.** When the owner says in advance to follow the recommended options without asking, still write the short and full plans and record the message with `ase task approve TASK --proposal-hash <hash> --owner-preapproved --user-message-ref <that message>`. A general go-ahead covers routine choices within scope. For a HIGH or MEDIUM choice, show the rationale before editing and cite approval covering the named change or an explicitly delegated, bounded choice. Proceed with independent approved work while the decision is pending. Infrastructure files and dev apply need the corresponding permission. Get separate explicit approval before merging to production or changing production infrastructure. Follow [questions and approval](references/questions-and-approval.md) for production and shared data. Report the material decisions taken and their approval basis.
- Declare a background process, polling, a global UI effect or a shared-service change in the proposal `effects` before the first edit ([scope growth](references/scope-growth.md)). State `non_goals`, `unchanged_behavior`, rejected `alternatives` (option, why_not) and `rollback` when they matter to the reviewer; for auth, untrusted input, secrets, permissions or outbound calls name the relevant STRIDE threats and their handling.
- Record the approved plan against its exact version/stages, then proceed without asking again for the same work. Re-check gaps after discovery and answers. [Questions and approval](references/questions-and-approval.md) covers real business/access/authority decisions; routine technical choices stay autonomous.
- LOW risk, one stage, up to 15 files / 300 lines: `ase task quick --base <default branch>` records scope, discovery and the proposal in one step; show the short plan and approve with the owner's reply. The change must add or change a test file (Markdown-only changes are exempt), or `finish` refuses it. Anything larger, riskier, touching infrastructure or a bugfix uses the full path (`ase task create --file task.json --bugfix`; the flag exists only at creation and the quick lane cannot carry bugfix evidence); adding `test_adequacy` on revise moves a quick task there.

## Execute

- Work through the local `ase` CLI with the configured backend; in project-local mode use `.devframework/bin/ase.ps1` or `.devframework/bin/ase` (never another project's home). A missing optional integration is not a blocker. Confirm independent-session capability before promising verification; an installed skill or fixture is not a live backend. Never copy credentials or change provider permissions to make a capability appear.
- Authenticated services: [local credentials](references/local-credentials.md). Use references and the local executor; configure a supported CLI recipe within the approved bounds before asking the user about a setup detail. Credentials never expand task authority.
- Independent ready parts may run as native subagents under [parallel work](references/parallel-work.md): register with `ase delegation`, commit the dispatch before spawning, record the handle and sealed result. Unknown launches are reconciled, never replaced on timeout; serial work is always allowed. A brief carries the solution rules above and asks the question, not a chosen fix: state the lead's idea as a hypothesis to test. A worker that finds an existing or better-placed mechanism reports it even when the brief did not ask.
- Keep the original chat as lead and process its [coordinator inbox](references/coordinator-events.md) after results and before completion. Notifications never expand authority or start another lead, and informational events do not trigger new verification loops.
- Software: enable test adequacy and save a requirement/risk scenario plan before implementation ([test adequacy](../quality-gate/references/test-adequacy.md)); close coverage gaps without waiting for an owner prompt; excluding tests from publication still allows local testing. Quick-lane tasks skip this separate assessment. Diagnose and fix a flaky or failing test this task changed or broke; another pre-existing failure is an [out-of-scope discovery](#out-of-scope-discovery). Never retry, skip or quarantine a test without the owner's decision. A new third-party package needs a stated reason, a license check and a pinned version.

## Verify and finish

- After implementation and checks, perform the contract's [additional original-main-bot passes](references/lead-critical-passes.md) (one for LOW/MEDIUM risk, three for HIGH) against the original requirements and approved clarifications: record before fixes, recheck after, keep a current final assessment. An awaiting-lead-review handoff is your next action, not an owner question; workers and reviewers do not replace these passes.
- Run meaningful checks ([profile evidence](references/profile-evidence.md)) and separate independent acceptance and review against the original request. Before software review, ensure decisive unchanged examples and affected callers are recorded as read-only discovery dependencies. Add missing evidence through discovery or revise. Review the final diff for placement, readability and changes beyond the approved plan. For a nonobvious public signature change, include one line in the PR explaining why callers need the change. Software keeps positive executed test counts and successful mandatory checks. P0/P1/P2 block; P3 is advisory. `ase --project PROJECT gate TASK` decides; a finished process or a written PASS is not approval.
- A request to "review" work this session implemented goes to an independent review session; without one the review stays pending, and any review you do yourself is a "self-check, not independent", never an approval.
- Fix loop before push: after any fix commits, an independent reviewer reviews only those commits, reader pass included; then `ase task finish`, then push. A fixer's self-check never counts as that review.
- Repair in-scope findings, rerun affected checks and fresh independent AC/review; no unrelated refactoring. A finding that the change fixes a defect outside the ticket is repaired by deleting that fix, never by moving it to another branch or PR ([out-of-scope discovery](#out-of-scope-discovery)). A blocking finding you disagree with stays blocking until fixed or until the owner decides; only then run `ase task dispose-finding TASK --finding <id from ase task findings>` (waive P2, disprove any) citing the owner's message: `prompt:<id>` from `ase prompt list`, or the chat reference with `--owner-quote` and the owner's exact words. Never dispose on your own judgment or with words the owner did not write.
- Progress-mode tasks reassess after three consecutive cycles without verified progress on the same problem (newly satisfied obligations or eliminated failures; prose and renames do not count). A supported diagnostic probe may continue, but failure without verified progress stops automatic changes. Respect hard limits, hold work behind unresolved blockers and reconcile UNKNOWN external effects before retrying ([stopping and recovery](references/stopping-and-recovery.md)).
- Outside the framework's own repository the framework is the owner's private local tool. Push only the task's own changes: never stage, commit, push or put in a PR framework skills, agents, instructions, memory, runtime, CI or hooks, and never mention the framework, `ase`, its gate, lanes or evidence in commits, PR descriptions, code or messages to others.
- Before any push or PR by any route (git, gh, az), commit and run `ase task finish TASK --base <default branch> --body-file <file outside the repository>`; the base is the branch the change merges into (for example `origin/main`), never a commit; a deliberately created branch can bypass this local check, so server-side CI against a trusted base is the real enforcement. READY means the gate approved this clean HEAD and `ci-check` passed; use the file as the PR body. REVIEW means owner decisions rest on words you supplied (read `status`; NOT_READY shares exit code 2): show them to the owner before pushing. An `--allow-*` exception needs the owner's `--override-ref prompt:<id>` (or a chat ref with `--override-quote`). Otherwise fix the listed reasons or put owner-review items to the owner.
- A workspace may hold one or more independent nested clones (not submodules) declared in the root `.meta` (`{"projects": {"src/orders": "<url>"}}`) or as `repositories = ["src/orders"]` in `.devframework/config.toml`; one installation at the root serves them all. One task changes one repository: keep its scope under that clone (a scope across clones, or a clone plus root files, is rejected: make one task per clone). When the branch may already hold work, add `"repository": {"path": "src/orders", "base": "origin/master"}`, so the baseline, `source_changes`, `_ase_context/source_diff.patch` and `_ase_before/` come from that base. Snapshot, `finish --base`, ci-check, clean-tree, secret and publication checks then run in that clone's Git (`ase authorize --repository src/orders` for its remote). Evidence commands still start in the workspace root, so give them the clone path. Changing `repository` path or base on an approved task recomputes its baseline from the new base ref (recorded in history); without a base ref `revise` refuses, so set one or create a new task.
- Large mechanical changes: the full-copy packet may not fit. Ask the owner to approve `review_packet` `diff_context` (diffs with context; never chosen by size) and, if the error proposes one, a split into `parts`; the gate then requires every changed file in exactly one independently reviewed part. A project check script an evidence command runs from the private installation is declared in `check_inputs` (only `.devframework/local/checks/`); it should print one result per rule (what, threshold, violations) and have a sensitivity run with an injected break that must fail. Reviewers never fetch extra files mid-session.
- At completion, approval wait, blocker, pause, cancellation or stop, save a dated session closure with one exact next action ([finish and reports](references/finish-and-reports.md)); never claim completion you do not have. Publish or send only under explicit destination authorization; publication defaults to a dry run.
