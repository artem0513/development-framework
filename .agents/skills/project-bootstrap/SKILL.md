# Explicit workspace adoption

A template, installed runtime or readable workspace does not adopt other projects. Prepare tooling separately from project routing. Activate only the explicitly selected existing project/workspace and backend targets; no Git repository is required. Preserve applicable local instructions and existing user authorization.

For the user's requested all-in-project installation add `--project-local`: preview `python scripts/install.py --project PATH --project-local --target codex --preview` from the framework source, adding `--target claude` or `--target copilot` only when selected. Review exact owned files, hashes, scope and private backup paths before applying. Runtime/settings live in `.devframework`, private memory/journal in its ignored `local` child, and commands use `.devframework/bin/ase.ps1` or `.devframework/bin/ase`. Without that flag existing shared adoption remains available; `--runtime-only --target BACKEND` prepares shared tooling without routing. Never change authentication, unrelated integrations or provider permission settings as a setup shortcut.

Outside the framework's own repository every installation into a Git project is private: instructions go to local-only files (`AGENTS.override.md`, which tells Codex to read the team's `AGENTS.md`; `CLAUDE.local.md`; `.github/instructions/devframework.instructions.md`), every owned path is listed in `.git/info/exclude`, an earlier managed block is removed from the team's own instruction files, and files Git already tracks are refused. Nothing the framework installs may be committed or pushed there; only task changes are.

After installing, propose 3-5 short project hints to the owner and write the lines they confirm to `.devframework/hints.md` (UTF-8, at most 4 KB; excluded from Git in a private install, also before it exists). Hints are structural: what ordinary search misses (nested or sibling repositories, handlers registered by name), which external systems are documented where (read those docs instead of asking), which undocumented external systems the owner must be asked about, and who owns what. Never put a ticket's answer, a known bug, credentials or anything not confirmed by the owner in a hint. Reinstall to copy the hints into every local instruction file. Hints apply only to private installs (not the framework's own repository or a project outside Git), and the file is the owner's only copy: `git clean -fdx` deletes it, so keep a copy elsewhere. Measured: these lines helped where they pointed (eval round 11), while generated project maps and a mandatory tracing rule did not.

Register project identity with the local `ase` CLI; new projects use `local` reporting time from the executing computer, so a region is not a setup question. Respect an explicit existing timezone selection; inspect actual source inventory, domain constraints, checks and capability versions. The bundled project profile is a worksheet, not an access grant. Use task-discovery to record tool presence separately from permission, resource access, structured output and independent execution.

Use software checks for code/config implementation, domain evidence for documents/research, and real resource observations for infrastructure. Native role pointers and protocol tests do not prove live model support. Missing subscribed backends remain explicitly unavailable; do not install them merely to complete a support matrix.

Read [skill routing](references/skill-routing.md) when selecting optional methods. Inspect and pin a vendor package before explicitly scoped copying; downloaded scripts are not executed. A shared runtime never activates project routing globally.

## Re-review after updating the policy

When a preview reports `review_policy_changed: true`, record the pending review follow-up in the update task before applying. Retain the reviewed preview to resume after interruption. Once applied, inventory open PRs or MRs for the updated project within the approved scope. Use the authorized repository provider read-only and identify the exact head and base for each. A shared-runtime update follows the same review for affected adopted projects within the update's scope. Use current rules to re-review each whole open diff against its task, including scope, fixes at the source, cross-service contracts and removal cleanup. For managed PRs, restore the original task and refresh affected checks and independent review against the current policy and source. For other PRs, record the read-only review and its evidence limits. Record each head and outcome or blocker in the ongoing update task. A no-op reapplication leaves any outstanding review work pending. If access is unavailable, report the specific gap and any verified local work. Re-review grants no permission to edit, push, post, change PR state or fix unrelated defects.
