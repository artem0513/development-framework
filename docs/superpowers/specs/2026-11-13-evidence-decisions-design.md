# Evidence decisions: six workflow rules

The owner approved implementation of the six recommendations from the shared-chat review, actual Codex testing, independent review and publication to the existing repository. Routine decisions are delegated; clear tasks must keep moving without another approval interview.

## Design

Use one conditional reference and a small evidence-brief asset inside the existing task-orchestrator skill. Intake/discovery, execution, memory, AC and substantive review link to the relevant rules. Keep the existing eleven entrypoints, local CLI, SQLite fields, checks, approval boundaries and project-local installation. These are semantic workflow instructions, not new runtime enforcement or a new state machine.

1. Identify the actual target and the authority/role of any comparison reference, including inherited versus task-owned behavior.
2. Bound observations and negative claims; a blocker names a required outcome and a concrete failed check, with useful authorized alternatives investigated.
3. Distinguish dependency promises, existence/metadata, access, completeness, data suitability and consumer behavior; check only what the actual obligation needs.
4. Give actionable artifacts a purpose, state and version. Check unresolved placeholders and freshness before authorized execution/handoff; new evidence updates affected artifacts and conclusions without replaying effects.
5. Preserve required semantics in migrations/optimizations with meaningful equivalence checks; keep preexisting ambiguity separate from a new regression or an owner-only business decision.
6. Trace review claims through actual callees/contracts and evidence before applying repairs; missing evidence stays a coverage gap until investigated.

The brief is conditional and concise. Ordinary clear work uses existing notes; it does not require a universal questionnaire or a new approval. Store its facts/references in existing checkpoint, intake, knowledge and dated journal fields; unknown JSON keys remain unsupported. No credentials or raw conversations are retained.

## Approach and limits

Extending existing instructions fits this change. New runtime/schema gates would imply mechanical proof of semantic authority or correctness, add migration cost and exceed the need. A twelfth skill or another orchestrator would duplicate routing. This choice is an implementation decision within the approved scope.

Canonical content lives under skills/. Sync the adopted repository's tracked .agents copies; the current recursive installer delivers the same reference and asset to Codex, Claude and Copilot. Live behavioral acceptance covers Codex only; packaging checks cover all three. No real cloud, database or external service mutations are part of the tests.

## Acceptance

Preserve immutable baseline inputs and five fresh Codex sessions before edits. Run five fresh sessions with the candidate, examining concrete decisions/artifacts under eight fixed scenarios, including clear-task and newly-resolved-decision controls. Do not invent baseline failures or mistake protocol/static checks for semantic judgment. Run meaningful installer/link tests, current test suite and existing assets/whitespace checks. Obtain separate genuine current-source AC and substantive review; repair confirmed findings, recheck and publish only after the real gate approves. Confirm remote SHA before dated closure.
