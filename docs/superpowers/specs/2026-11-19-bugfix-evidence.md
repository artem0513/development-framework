# Evidence for bugfixes

For software bugfixes, distinguish a reproduced symptom, a supported cause and
a proposed correction. A green helper test or an endpoint becoming reachable
does not establish the cause or justify a new merger, wrapper, cache or retry.

New bugfix tasks explicitly enable version-1 `bugfix_evidence` alongside test
adequacy. Legacy contracts remain unchanged. Save one compact investigation per
software stage with acceptance obligations in the existing hashed scenario plan:
empty coordination/delivery phases need no invented regression. Trace references
explicitly select current or authenticated before-source (default current), so
removing faulty code does not erase its causal evidence. Include expected/observed behavior,
first divergence, relevant caller/boundary/callee/contract trace, causal evidence,
cause status, fix rationale, considered alternatives and required regression
scenario IDs. Hypotheses and workarounds can be saved for continued investigation;
they cannot pass as a confirmed causal repair. Do not interrupt useful authorized
investigation or ask the owner about retrievable facts.

An independent adequacy session explicitly evaluates cause, fix necessity and
the regression chain. PASS requires current executed proof and observable source
locators; the actual causal/contract judgment remains semantic. The regression
must discriminate the original failure through the real consumer boundary and
protect other contractually legitimate behavior. Mocks/fixtures need a grounded
contract, not expectations invented to match a new helper. Baseline failure,
captured boundary observations or a supported fault injection can discriminate
the cause; do not require destructive reproduction in a live environment.

AC and substantive review independently challenge the same claims. Missing or
unavailable proof blocks verified completion, never fabricates a defect. Keep
the current stage's obligations explicit in host-computed verification scope;
downstream proofs remain pending rather than falsely blocking an earlier phase.
The whole-task gate still requires every mandatory obligation, and observable
current source defects remain actionable during stage review. Keep
runtime standard-library-only, separate review identities, existing stale-input
bindings, CAS/restart safety, scoped authority and publication rules. No database
migration, project-memory deletion or CostPP3/VM/database changes are in scope.
