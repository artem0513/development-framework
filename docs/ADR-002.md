# ADR 002 — Host-managed independent verification from a sandboxed chat

Status: **superseded for active runtime and installation** by [ADR 004](ADR-004.md), dated 2026-11-12. The material below is historical evidence of the former MCP solution, not current setup guidance. Existing user registration is removed only through a separately authorized preview/cleanup; it is never silently migrated.

Date: 2026-11-01. Scope: fix the reproducible nested Codex startup denial without weakening sandbox permissions or requiring a manual PowerShell continuation.

The direct nested CLI is not made privileged. A standalone `codex sandbox --permission-profile :workspace` probe proved that the real Codex home permits reads but denies an `r+b` open of `installation_id`. Codex's current in-process app-server startup requires that write/open/lock even for an existing ID. An outside-workspace write was denied while a workspace write succeeded. See the [official implementation](https://github.com/openai/codex/blob/main/codex-rs/core/src/installation_id.rs) and [Windows sandbox behavior](https://learn.chatgpt.com/docs/windows/windows-sandbox).

Use a narrow stdio MCP coordinator, started by the Codex host before tool sandboxing. Its only exposed operations start independent verification of an existing task and read that job's status. The chat continues to create the contract, implement and run checks in its original workspace sandbox. The coordinator never runs contract test commands, implementation, authorization or publication. It launches two separate Codex verification sessions with `--sandbox read-only`; model responses alone cannot approve the gate.

Host configuration pins allowed repository roots, state home and an absolute Codex executable. Requested paths are canonicalized; Git metadata, common directories and state/evidence redirects cannot escape those boundaries. Python `-P` prevents repository package shadowing. Git inspection uses a separate adapter that disables fsmonitor, external diff/textconv, clean/smudge/process filters, hooks, ambient Git configuration and remote protocols. Publication retains the normal Git hook behavior; the host adapter rejects mutation commands.

Reviewers start in the trusted installed runtime, so target `.codex/config.toml` cannot introduce new host MCP processes or hooks. The absolute repository is supplied in the handoff, and commands can inspect/test it read-only. `--skip-git-repo-check` permits the trusted non-repository startup directory; it changes neither filesystem nor network permissions. The coordinator's own MCP server is disabled in those children to prevent recursion. All subprocess stdin is DEVNULL, separate from the live MCP JSON-RPC channel.

The user requested automatic independent verification. Configure `approval_mode = "approve"` only for `verification_start` and `verification_status`, with an explicit tool allowlist and a prompting server default. This is the [documented MCP per-tool permission mechanism](https://learn.chatgpt.com/docs/extend/mcp); it does not change the chat's sandbox or global approval policy. Configuration changes are backed up. No credentials are copied or linked, no ACLs broadened, and no sandbox bypass flag is used.

Registration is scoped to the explicitly configured root `E:/Tools/DevelopmentFramework`, including disposable child repositories. Additional projects require an authorized bootstrap registration of their root; the tool cannot grant itself more roots. A newly started Codex chat loads the registered MCP service automatically. Existing sessions that have not refreshed their MCP tool catalog remain safely BLOCKED rather than launching an unrestricted fallback.

The original same-user limitation remains: this local coordinator is not a protected CI identity or a tamper-proof publishing authority. Remote production enforcement is a separate task. Verification results still bind executed receipts and actual current source bytes.
