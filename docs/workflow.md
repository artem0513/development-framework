# Managed task workflow

New CLI root tasks require three additional critiques by the original main bot
after initial implementation/checking. Read the operational
[lead-pass reference](../skills/task-orchestrator/references/lead-critical-passes.md).
Every pass reconciles the original request and authenticated full approved
contract/proposal history. Default complexity is nontrivial; a current mechanical
LOW-risk exemption is independently challenged. Final completion, not each child
or intermediate stage, waits for this layer. Native bots execute the critiques;
ase stores CAS intent/results and recovers captured output without a new prompt.
Final independent AC/review binds the lead digest separately from reusable
stage/action context. Legacy saved tasks are not silently rewritten.

Explicit adoption of a selected project/workspace activates this workflow. It supports software, infrastructure, documents, research and mixed work. A template, shared runtime or optional integration does not activate other projects. Ordinary questions use their domain workflow without a managed contract. Choose profiles by actual action: financial report warnings do not turn analysis into software debugging.

Use the installed `ase` / `ase.ps1` launcher, or `python -m ase` in the source checkout. Global `--project PROJECT_ID` (or compatibility `--repo ROOT`) and `--home` precede the subcommand. State selection is explicit `--home`, selected project-local config, `ASE_HOME`, then the platform AutonomousSE directory. In [project-local mode](project-local.md) use `.devframework/bin/ase.ps1` or `.devframework/bin/ase`: settings/runtime are project-owned and memory/journal/receipts live in ignored `.devframework/local`. Local project UUIDs and explicit workspace aliases isolate the memory; Git is not required.

## Intake and discovery

For comparisons, blockers, dependencies, actionable artifacts, semantic changes and disputed findings, use the [six evidence decision rules](../skills/task-orchestrator/references/evidence-decisions.md) and, when useful, the [current evidence brief](../skills/task-orchestrator/assets/evidence-brief.md). Establish the target and reference authority, bound claims, verify the required readiness, distinguish artifact purpose/state/version, preserve required semantics and substantiate review through actual code/evidence. Refresh affected artifacts and conclusions after new answers. These instructions reuse existing memory/checkpoint fields; they add no universal form, service dependency or renewed approval for clear authorized work.

Check the assignment for obvious omissions, contradictions and uncertain intent before implementation. Retrieve existing task identity, `context`, fresh relevant project/meeting knowledge and `restore TASK` before replacing a task or rescanning known facts. Reconcile current observations with saved state; preserve newer user work. For assignments/meetings use task-intake, separating required outcomes, constraints, decisions, suggestions and unknowns with document/user-message/timestamp references. A participant's suggestion is not approval or an external-action grant. Raw recordings and full transcripts stay outside SQLite. Re-evaluate the gaps after discovery and material answers.

Inspect named resources first. Expand only to material dependencies or questions relevant to the requested outcome and record why. Use task-discovery to inspect applicable instructions, source versions/freshness and actual capabilities. A commit does not cover dirty/untracked content or external settings. Refresh affected knowledge and dependent records while retaining provenance/history. Read skill metadata first and load bodies/references only for the active step; optional methods do not start a second orchestrator.

Before a material question, use the [answer-investigation workflow](../skills/task-discovery/references/answer-investigation.md). Select relevant authorized evidence: current code/contracts, Git/PR/ADR rationale, bounded logs/traces, schema/migrations, read-only incident data and related service/repository contracts. Restore fresh knowledge first. Distinguish observations, an intent hypothesis and the recommended solution; current behavior does not establish future business authority. There is no default pass count, research cost or time budget. Continue discriminating checks when actual new information or a credible lead gives the next check a useful prospect of resolving the uncertainty. Repeated synonym searches with no new information do not justify continuing. Stop on sufficient evidence, no useful lead, unavailable required access without an authorized alternative, an owner-only decision, an explicit existing limit or the user's stop. Optional unavailable sources do not block independently approved work. Save concise provenance, uncertainty, next lead/stopping reason and actual effort rather than raw logs/rows. Resume/delegates share history and explicit bounds. These are portable guidance, not a runtime semantic search-enforcement claim.

Before proposing implementation, also perform a bounded search for relevant existing project examples, including appropriate shared packages and sibling microservices in the authorized project/workspace. A relevant precedent need not be a runtime dependency. Record the inspected source, intended reuse and compatibility reason; a single example is not automatically a team standard. Prefer applicable documented rules and maintained compatible code; do not copy retired or unsafe behavior. Existing knowledge can identify candidates but its sources must still be current. An inaccessible external example does not replace useful local search or automatically block the task. See the portable [project-example workflow](../skills/task-discovery/references/project-patterns.md).

An explicit user instruction not to use templates/examples or not to search for analogues disables deliberate example search and reuse for that task, including cached/delegated examples. Continue necessary target/dependency inspection and mandatory project rules. State found example / no suitable example within the searched scope / skipped by user in the existing concise proposal's reuse line. Do not ask the user to select routine patterns when a safe project-supported choice is available.

Capability evidence separates presence/version, permission, structured output, resource access and actual independent sessions. Unknown is unavailable until probed. Local CLI adapters are sufficient; no framework MCP service is required. A protocol fixture or installed native role does not prove a subscribed backend or live independent session. Report unavailable infrastructure without copying credentials, relaxing permissions or installing unrequested products.

## Proposal and authorization

A clear assignment authorizes investigation. Changes to code, tests, data, configuration or infrastructure start once the owner approves the implementation plan. Keep a concise proposal covering the result, approach, reuse, verification and material assumptions. Record the owner's approval against the exact proposal and stages. Reuse authorization when the owner already approved the same outcome and scope.

Ask for genuine unresolved business/access/authority blockers or serious architectural changes beyond the assignment, after useful relevant investigation cannot establish the answer or only the owner can decide. Choose routine technical details yourself using project rules and suitable colleague examples. Use roughly 4–6 lines: uncertainty; inspected evidence; unconfirmed intent hypothesis; recommended solution and why; one concrete decision. Keep the hypothesis separate from the recommendation. Hold explicit affected known stages and dependents; absent/ambiguous impact mapping stays conservative. Continue independently approved work. After the answer refresh affected assumptions/contracts/evidence and check remaining gaps. Route unresolved task questions to the owner first; if team input is needed, prepare the concrete question and send only after approval of its content and destination. Standing channel permission does not bypass that review; reuse approval of an already approved concrete question.

Persist the exact proposal hash, contract revision, approved stages, observed original user-message reference, timestamp and external-action bounds via task propose/approve. A proposal may declare `effects`: each new background process, polling, global UI effect, shared-service change or changed report meaning names what changes, its `basis` (`REQUIREMENT` bound to a source ID with a locator or an acceptance ID owned by every affected stage, `DECISION` also to a resolved unknown with a recorded resolution that covers those stages, or `ASSUMPTION` bound to an unknown that blocks those stages) and the scenario the existing path does not cover. Propose, approve and stage start reject unbound or prose-only justifications; approval and stage start hold stages on an unconfirmed assumption. The host checks binding, not meaning; ordinary changes declare nothing. A boolean or invented message reference is not approval. Reuse existing authorization for the same outcome/scope. New business meaning, serious architecture, material risk/cost, resources or external authority beyond the assignment require revised approval. Internal decomposition may create subset stages without removing parent obligations. Execution-plan changes require fresh affected evidence without automatically revoking business approval; unchanged independently approved stages retain it.

## Execution and evidence

Commands are authorized for their actual stage immediately before process creation, including after authentication. Final authority validation and process creation share a short transaction with contract revision, stop and cancellation. Stops and cancellations apply through every ancestor; active commands are cancelled when that authority is withdrawn. Cancellation cannot undo an external effect already applied, so interrupted submissions still require reconciliation before retry. Task-wide checks select currently authorized stages. Completed prerequisite stages require fresh checks and independent verification before dependent work; this never replays their implementation or mutations.

For required/optional source inputs, intentional output absence, and hash-bound readable representations of binary artifacts, see [source availability and artifact evidence](source-evidence.md). Representations prove the identity of reviewed bytes; the independent domain reviewer judges whether they adequately represent the native artifact.

Linked checks belong to the stages whose acceptance criteria name them. A shared check must be linked to each relevant criterion or left unlinked as a common task check; a mandatory test of a deferred stage is never implicitly authorized elsewhere. Check-specific scope and credential targets must fit the selected approved stage. Each software stage still needs positive executed test evidence, and the final gate still requires every mandatory check. Explicit resume may clear only that task's own stop; ancestor stops and cancellation remain effective.

Use the configured local backend adapter and relevant domain skills. Preserve platform permissions. Perform real checks appropriate to the acceptance profile and keep executable facts separate from model judgments:

| Profile | Required evidence |
| --- | --- |
| software | Mandatory successful commands, positive executed tests, no skipped required tests, independent AC/code review, current source/contract/plan fingerprints |
| infrastructure | Actual resource IDs, before/after observations, recorded intents, reconciliation and independent postconditions |
| document | Required artifact/content, readable rendering when relevant, traceable sources and independent acceptance/substantive review |
| research | Dated sources, claim coverage, explicit inference/uncertainty and independent acceptance/substantive review |
| mixed | Mapping and complete coverage of all mandatory parent and child obligations |

`check TASK` executes configured checks; review argv before running project scripts. `verify TASK` captures separate independent acceptance and substantive review sessions through the authorized adapter. A model reply alone is not a runner receipt. Verification uses original requirements, actual current artifacts and execution evidence, rather than trusting an implementation summary. Missing independent execution remains BLOCKED.

`gate TASK` validates current evidence and profile coverage; exit codes are 0 APPROVED, 2 REJECTED, 3 BLOCKED. P0/P1/P2 block approval; P3 is advisory. Missing, stale, tampered, expired or forged evidence cannot approve. Session closure and process exit zero do not establish completion. Only satisfied current obligations plus APPROVED permit COMPLETED.

Allocate proof by the [causal readiness boundary](../skills/task-orchestrator/references/evidence-decisions.md#3-check-the-readiness-the-obligation-actually-needs): a criterion cannot require its own AC/review/gate approval or an effect that approval authorizes. Publisher uses the whole-task gate, so moving publication proof to another stage of that task still creates a cycle. Keep the gated source-acceptance contract phase-local and retain actual publication, required remote/local SHA agreement, consumer postconditions and closure as applicable in an explicit mandatory publication/finish plan or separate delivery task. Verify those after the authorized action before claiming the overall assignment complete. Reuse existing authorization for this allocation; preserve independent AC/review and every original obligation.

## Optional parallel work

Parallel work is optional when at least two ready parts are independent and native host/provider subagents are available and permitted. One lead retains the approved goal, scope and budget, assigns each bounded goal/read-write ownership/inputs/output/acceptance/dependencies, gathers results and integrates before final affected checks and independent review. Use separate authorized workspaces for disjoint mutations or return proposed edits to the lead; preserve shared-root execution leases, CAS and actual receipt capture.

Recompute the dependency graph's ready set after every result, failure, new dependency or capacity change. A sequence of ready waves may be 1 → 4 → 1 → 5; concurrency is bounded by actual provider slots, resources and remaining budget, and excess work waits in a queue. Dependencies and integration barriers can reduce concurrency, then release more work. This internal scheduling needs no repeated interview within approved scope. Trivial work or unavailable optional native tools uses the serial path; no second coordinator, parallel SDK or MCP is mandatory. Advisory native answers are not formal AC/review receipts. Read the conditional parallel-work reference in the canonical orchestrator package when dispatching.

This policy combines dynamic worker decomposition and synthesis ([Anthropic](https://www.anthropic.com/research/building-effective-agents)), a lead retaining the answer while using bounded specialists ([OpenAI](https://developers.openai.com/api/docs/guides/agents/orchestration)), runtime-sized fan-out and deliberate state merging ([LangGraph](https://docs.langchain.com/oss/python/langgraph/graph-api#send)), and dependency/context/integration planning with coordination costs ([GitHub](https://docs.github.com/en/copilot/concepts/agent-capabilities/choosing-and-delegating-agent-work/delegating-and-parallelizing-work-with-agents)). The lightweight ready queue and optional native delegation are this framework's design inference; no new SDK, LangGraph or MCP dependency follows from those sources. Worker results carry status, evidence, proposed/actual changed paths and blockers so the lead can validate and combine them.

The original chat owns the [durable result inbox](../skills/task-orchestrator/references/coordinator-events.md). `ase events` binds its exact endpoint, preserves immutable producer identities and separates delivery from processing. Native hosts may return service events to that chat; the active lead can consume them directly without a transport. Unknown delivery and claimed processing never expire into permission to repeat work. Recovery includes captured terminal failure outcomes as evidence, never successful acceptance. No external idle desktop wake-up is inferred from a CLI or share link.

New CLI software tasks enable [independent test adequacy](../skills/quality-gate/references/test-adequacy.md). `ase adequacy plan` records required scenario/consumer-boundary obligations; `verify` runs a distinct adequacy session in addition to AC/review, and the gate rejects missing, insufficient, stale or reused proof. Saved unconfigured contracts keep their identity and disclose that status. Test generation remains bot-owned; no passing count or mechanical rule proves exhaustive bug absence. The lead handles material current coverage gaps before reporting completion.

## Progress, repair and stopping

For a repair under the approved plan, change the implementation and refresh its checks and review. Additional checks can be saved with `task plan` within the current approval. Resubmitting identical normalized contract or proposal data preserves the current approval and execution plan. Separate owner replies for the same proposal accumulate stage approvals. Each stage retains its own grant until the owner explicitly approves it again. A changed contract or proposal requires fresh approval. A reference already used for an earlier proposal or a narrower stage grant cannot stand in for a fresh decision. The host request includes the saved proposal and its approved stage IDs in `handoff.task_proposal`, so acceptance and review can check decisions recorded after the original ticket.

For a child task, `handoff.task_proposal.ancestor_proposals` carries the saved plans for the approved stages it inherits from. The host checks the current parent bindings before preparing the request. The child's approved scope determines which changes it can make.

`ase task findings TASK` shows the independent finding journal. Material findings retain their IDs and state across passes and approved revisions of the same stage. A fresh reviewer explicitly closes an earlier finding with current packet evidence or leaves it open. A missing follow-up holds the gate. A resolved entry stays in history, and new evidence of a regression can reopen it under its existing ID even if its line moved. The current independent judgment and executed checks remain required. Owner dispositions retain their existing contract and scope bounds. Split-part findings keep their own independent follow-up.

Automatically repair actionable in-scope findings, then rerun affected checks and fresh independent AC/review on current artifacts against original obligations. Existing authorization covers those corrections; avoid unrelated refactoring. New `templates/task-v2.json` contracts use `recovery_mode=progress`, `stagnation_limit=3`, `repeat_failure_limit=2` and `diagnostic_timeout_seconds=1200`, with null default stage/task cycle caps, total diagnostic-pass cap and active-time budget. Saved legacy policies and explicit hard limits remain respected; no migration silently enlarges them.

Three consecutive unsuccessful cycles without verified progress on the same underlying problem trigger reassessment, not a total task-attempt ceiling. Progress means newly satisfied original obligations or verified elimination of a failure, supported by fresh checks and required independent judgments. Edited bytes, new prose/hypotheses, different error wording and oscillating re-satisfaction do not count. Original-problem history survives aliases, renamed/decomposed stages, delegates, resume and contract revisions. A recurring cause is also diagnosed under the persisted repeat-failure policy. Monotonic verified progress can continue beyond three total cycles while explicit limits remain in force.

Persist diagnostics before launch. Reassessment may support a concrete in-scope corrective probe with actual new evidence; after that probe require verified progress to resume normal repairs. No progress stops automatic mutation. Do not create an endless diagnostic chain from identical evidence or reopen a consumed probe after a crash/resume/rename. Reconcile genuinely new discriminating evidence or changed external state with the stopped record before another supported probe. Use bounded provider/client policies for temporary service retries. Useful discovery information and verified implementation progress are distinct.

A runtime-policy change (an `ase` upgrade or skills update) makes completed stages' AC/review receipts historical, because the source fingerprint includes the policy identity. When a completed stage was proven by genuine independent sessions and today's artifacts, read under the receipts' historical policy, reproduce the approved fingerprint, `resume` refreshes it with fresh checks and independent AC/review under the current policy, keeping the original implementation receipt as provenance; no new implementation cycle runs. A current independent rejection demotes the stage to `REFRESH_REJECTED` and the normal repair cycle follows; any other non-approval blocks. Changed source still needs a new implementation cycle.

Inspect blocked reasons separately: unresolved blockers hold affected mutations even when the gate is REJECTED. Explicit known stage mapping can preserve independent approved work; missing or ambiguous mapping stays conservative. Explicit resume can probe restored checks/verification without resetting history. Mandatory capability gaps and new material conditions stay explicit; do not weaken tests or downgrade findings to obtain approval.

Persist stable operation IDs and intents before effects. Keep the same logical action ID across retries and recipe edits; intentionally distinct authorized effects need distinct logical IDs. A changed recipe cannot discard known application history. Lost acknowledgment after an attempt is UNKNOWN: reconcile the operation and actual resource before retrying. `visible=false`, empty eventually consistent lists and unavailable observations do not establish nonapplication. Resolve UNKNOWN only with proven application or authoritative terminal absence/nonapplication before deciding a safe retry. For automated terminal-absence reconciliation, the effect command must emit complete JSON containing its actual `provider_attempt_id`; the observation must identify that same submission and assert `absence_confirmed: true`. Missing or stale binding remains UNKNOWN; a fresh local log pathname is not new provider proof. Same-root stage aliases and delegates reuse logical operation history. A recipe edit or relabelling cannot prove that an unresolved effect is independent: overlapping or unknown resource footprints require reconciliation before another mutation. Known disjoint approved targets may continue; recipe text is not a stable external-operation identity. Distinct logical action IDs can represent intentional repeated effects once earlier effects are known. Preserve case-sensitive URI paths and opaque resource IDs when establishing identity; ambiguous aliases may block work, but must not prove two resources identical. Recipes remain responsible for truthful provider observations. Do not recreate/deploy/roll back blindly. On stop, stop scheduling mutations, account for active effects and save a checkpoint/dated closure. A hard kill preserves only the last completed transaction.

## Closure, memory and reports

Use revision-checked `checkpoint` and `session finish` records with concise results, actual checks, decisions, blockers, evidence references and one next action. The closure key/payload is idempotent; conflicting content or stale CAS requires reconciliation. Reasons include completed, awaiting approval, blocked, paused, cancelled and interrupted. Closing the session does not silently complete or cancel the task.

Use task-orchestrator's conditional finish-and-reports reference for the current CLI payload. Store occurred UTC separately from recorded UTC and retain corrections. `worklog --from DATE --until DATE` reports dated events; `meeting-report` adds results, decisions and carried blockers, with historical `--as-of-end` separate from current status. The upper date is exclusive. New projects default to `local`, using date-specific OS rules on the executing computer. Explicit project/CLI timezone selections remain supported; missing rules for an explicitly named zone block rather than silently falling back. UTC event storage is unchanged.

Local memory holds concise source-backed facts, versions and history, not raw chats, full transcripts, recordings or credentials. There is no automatic multi-computer/cloud synchronization. Export/import is an explicit reviewed transfer. Reports are drafts unless the user authorized a destination; measured agent runtime never becomes inferred billable human time. Legacy daily/weekly time-entry semantics remain unchanged.

`report TASK` distinguishes implemented work, executed checks, independent judgments, unavailable checks and actual publication. Publishing is a dry run unless explicitly authorized for the exact remote; protected-path/high-risk controls and Git hooks remain in force. Never force-push or auto-merge. Local receipts are not a security identity: enforce publishing using trusted CI and server policy. [ADR 004](ADR-004.md) explains the portable CLI boundary and the historical MCP transition.
