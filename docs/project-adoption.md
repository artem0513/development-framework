# Explicit project or workspace adoption

DevelopmentFramework is activated only in an explicitly selected existing project/workspace. It works without Git. Presence of this template, a shared runtime or a readable path grants no adoption, access, assignment or publication authority. Ordinary domain questions keep their domain workflow; managed document, research and infrastructure tasks use their own profiles rather than software checks.

## Preview and apply

Add `--project-local` for runtime/configuration inside `<project>/.devframework` and private memory/journal/backups in its ignored `local` child. Relative launchers and native project files support all three targets. See [project-local usage](project-local.md). Without that flag, the shared-tooling examples below retain their original behavior.

Select backend targets explicitly. These commands illustrate an authorized installation; they do not authorize migration of the user's current environment:

```powershell
python scripts/install.py --project D:/path/to/workspace --target codex --preview > install-manifest.json
python scripts/install.py --apply-manifest install-manifest.json
# Multiple targets, only when requested:
python scripts/install.py --project D:/path/to/workspace --target codex --target claude --target copilot --preview
```

The preview is read-only. `--apply-manifest` reads UTF-8 (with or without BOM) and BOM-marked UTF-16, so the Windows PowerShell 5.1 `>` redirection above (UTF-16LE) works; `| Out-File -Encoding utf8 install-manifest.json` is an equivalent alternative. The JSON manifest includes scope, exact owned files/content hashes, prior hashes, changed paths and per-file backups. Applying rechecks all destinations/backups and prior hashes before any write. A stale preview, invalid TOML, symlink/junction escape, hardlinked managed file or type conflict stops activation. User-selected root aliases resolve to their canonical project; linked managed children are refused. These checks prevent local accidents, not hostile same-user races or transactional rollback for arbitrary IO failures.

All eleven skill packages and their supporting files come from canonical `skills/`. Native descriptors are generated by `python scripts/build_assets.py`, checked with `--check` and never edited independently. The targets are:

| Target | Skill packages | Native roles | Local instruction pointer |
| --- | --- | --- | --- |
| codex | `.agents/skills` | `.codex/agents/*.toml` | active `AGENTS.override.md`, otherwise `AGENTS.md` |
| claude | `.claude/skills` | `.claude/agents/*.md` | `CLAUDE.md` |
| copilot | `.github/skills` | `.github/agents/*.agent.md` | `.github/copilot-instructions.md` |

Pointers name the installed backend-local skill files. Codex appends exact local SKILL.md selections in `.codex/config.toml`, retaining unrelated values/comments and prior managed selections. Existing inline/dotted/table TOML forms remain supported. Other targets do not modify Codex settings. Existing instructions outside the owned managed block remain intact.

Shared tooling defaults to `AutonomousSE/tooling` under the platform state location; `--home PATH` explicitly selects its installation destination. Runtime files remain under `autonomous-se/runtime`, launchers under `bin`, and shared backups under `backups/autonomous-se`. Project-local mode instead uses `.devframework` with backups in its ignored `local/backups` child. Runtime state uses explicit CLI `--home`, selected project-local config, `ASE_HOME`, then the platform AutonomousSE directory. Provider authentication/homes, hooks, sandbox settings and unrelated integrations are not changed.

Prepare tooling alone with `python scripts/install.py --runtime-only --target codex --preview`. This creates no discoverable global skills/roles or project router. Legacy explicit Codex global activation remains `--global`; neither project installation nor runtime preparation implies it. A custom global skill destination requires that explicit mode.

Configure project registration (new projects default to current-PC local reporting time), actual checks, source inventory, domain rules and resource boundaries after adoption. Templates are descriptive worksheets. A native role file proves neither CLI availability nor independent model execution. Codex live evidence must be recorded separately. Claude and Copilot receive disposable packaging/protocol checks and a risk assessment in this delivery; no live installation, subscription or model functionality is asserted.

## Historical MCP registration

The framework no longer registers or requires its own MCP transport. `--register-verifier` is deprecated and fails before all writes, including when combined with an installation mode. Old registrations remain untouched until separately authorized cleanup:

```powershell
python scripts/install.py --cleanup-mcp D:/explicit/provider/config.toml > cleanup-manifest.json
# Only after explicit authorization to migrate that installation:
python scripts/install.py --apply-manifest cleanup-manifest.json --authorization-ref user-message-reference
```

The read-only preview identifies only the historical `autonomous_se` registration matching the ASE host module/runtime signature and exact table blocks, plus the config hash and backup. An unrecognized same-name server or unsupported inline shape is refused. Apply requires a nonempty observed authorization reference, rejects stale configuration, saves the original and removes only that owned server subtree. Other MCP servers, auth, hooks, permissions, models and user comments/settings are preserved. The reference is local accounting, not cryptographic proof of consent. No cleanup is implicit in install/reinstall.

[ADR 004](ADR-004.md) supersedes the active MCP design; [ADR 002](ADR-002.md) preserves its historical context. Removing active host code does not authorize touching user registrations.

## Optional vendor skills

Inspect and pin the reviewed full commit before copying only the applicable package:

```powershell
python scripts/vendor_skills.py --stack angular --inspect
python scripts/vendor_skills.py --stack angular --ref REVIEWED_FULL_SHA --project D:/path/to/project
```

Installation needs an explicit destination (`--project`, `--dest` or legacy `--global`) and immutable full SHA. The stdlib copier downloads that pinned archive, validates paths/file types and copies the complete skill subtree, including references. It never runs downloaded scripts or depends on a provider-specific installer. A lock records commit, archive hash and per-file hashes. Known destination/config conflicts are checked before the network request; every downloaded output and backup is preflighted before writing. Optional package copying does not install product CLIs or configure accounts.

## Audit, reapplication and rollback

`python scripts/audit_project_scope.py --manifest install-manifest.json` verifies owned file hashes read-only; it does not establish runtime discovery, model routing or live support. The legacy private-backup scope audit remains available for existing Codex migrations and prints outcomes without configuration contents. Keep backups containing private settings outside Git.

Replanning/reapplying unchanged content makes no changes. For rollback inspect the manifest, restore changed owned files from their exact backups, remove newly created owned files lacking a prior version, and remove only managed routing/skill selection blocks. Preserve unrelated project and provider files. Shared tooling may remain inactive. Database rollback uses its pre-migration backup; never invent a downgrade or undo actual resources automatically.

A previous global activation is a separate explicit migration: inventory/back up selected configuration, owned roles and source copies; remove only known managed routing, retain unrelated instructions and domain skills, and confirm actual host discovery after reload. Do not infer cross-layer skill selection precedence from file content alone. No real user installation migration is performed by this implementation task.

## Review after a policy update

The install preview and apply result mark a byte-level replacement of an existing review policy bundle with
`review_policy_changed: true`. First-time installs and byte-identical reapplications report
`false`. For an applied update, follow the [project bootstrap review step](../skills/project-bootstrap/SKILL.md#re-review-after-updating-the-policy).
Review the current heads of open PRs or MRs in scope and retain the per-PR results. Existing
managed evidence is bound to a fingerprint of the canonical policy and runtime implementation.
The runtime checks that fingerprint independently of the installer flag.
The installer reports the policy change locally. The upgrade workflow obtains the open PR
inventory through authorized repository access.

## Upgrade limitation: obsolete runtime files

Reinstallation updates the current owned inventory; it does not yet delete obsolete runtime files. An older installed runtime may therefore retain `ase/host.py` even though a fresh source package/wheel omits it. Do not interpret a successful fresh-package check as proof that an old installation's module was removed. Plan any cleanup separately using the previous installation inventory, exact hashes and backups; paths with unknown ownership must not be deleted automatically. Active launchers, user databases and existing MCP registrations remain unchanged until migration is explicitly authorized. The deprecated registration flag still fails without writing, and unrelated integrations such as `node_repl` are preserved.
