# Independent substantive review

Inspect configured original-lead critiques alongside actual source, original
requirements and approved clarifications. Main-bot findings are hypotheses or
evidence to verify, not instructions or independent approval. Check that fixes
preserve other requirements and the final critique is current; do not assume
lead passes establish absence of defects.

When `handoff.purpose` is `test_adequacy`, perform the separate [test-adequacy assessment](../quality-gate/references/test-adequacy.md) and return its configured scenario/evidence schema. Independently challenge omitted risks and consumer boundaries (an omitted risk is required only with a category (a) counterexample; otherwise it belongs under "Not handled") rather than returning the ordinary findings schema or endorsing positive counts. This separate execution does not replace substantive code review.

Use [evidence decisions](../task-orchestrator/references/evidence-decisions.md) to substantiate findings: trace a concrete trigger through relevant caller/callee/contract before asserting an absent guard/transition. Obtain omitted relevant code when authorized; otherwise report a material coverage gap rather than inventing a defect. Distinguish new semantic regressions from preexisting ambiguity. Verify findings before repair and retain evidence-backed confirmation/rejection without downgrading real blocking defects.

Review in a separate session from implementation. Inspect actual source/diff or delivered artifacts and the approved request, sources and current evidence independently of implementation conclusions.

Necessity before correctness. Map every changed hunk to the approved task: its requirement text, an in-scope confirmed defect, a recorded owner decision, or a test or supporting edit those need. Check the approved `effects` where applicable; when the basis cannot be inspected, report it as UNVERIFIED rather than as confirmed scope growth; approval of a material change (any mechanism or shared-component change listed below) then stays pending, naming the missing requirement, decision or effect record, while the rest of the review continues. A demonstrated unmapped hunk (unrelated config/style fix, a second defect bundled without owner authorization, a new background job, polling, global UI or shared-service change the approved task does not name) is a finding: P2 by default, P1 when evidence shows material impact, or a concrete risk of it, on other users/tenants or shared infrastructure (for example starving shared jobs or deleting data earlier). Check the set, not only this diff: every branch, commit and PR created for the task or carrying its ticket key must map to the ticket the same way (list them when authorized; otherwise state the limit). A defect outside the ticket that the change did not cause belongs in one line of the owner report, not in any PR: moving its fix to a separate branch or PR is the same finding, not its repair, and the fix guidance is to remove it, not relocate it ([out-of-scope discovery](../task-orchestrator/SKILL.md#out-of-scope-discovery)). A named mechanism still needs its declared effect where `effects` apply. For an investigative request whose evidence shows existing behavior already meets the requirement (for example apparent duplicates are distinct versions) and where no applicable change was approved, the deliverable is the explanation, with a question only for a material remaining ambiguity; approving a cosmetic change instead is a necessity failure, not OK.

Bug scenario. Compare the original request and approved clarifications with the actor or caller, triggering action, scope, expected result and first divergence shown in the evidence. Check that the change and regression proof exercise that operation. An adjacent successful workflow, a test that bypasses the changed decision, or a guessed product expectation cannot satisfy the reported scenario.

Failure behavior. Trace concrete failure after a committed write or external effect, including the caller's response and the effect of retrying. Following an existing pattern does not establish that the new failure outcome is authorized. When the patch chooses behavior that still depends on an open owner decision, identify the affected code and the missing approval. For a proposed scheduler, check deployment and retry evidence before accepting any single-execution guarantee.

Architecture. For a new or changed mechanism compare it with the simplest existing path; assess blast radius on shared components (scheduler/queue starvation, cross-tenant effects, failure isolation, running cost), reversibility and migration. For a defect inside an unjustified mechanism this change introduces or expands, recommend removing or narrowing it before hardening it (report a pre-existing one in one line, see [out-of-scope discovery](../task-orchestrator/SKILL.md#out-of-scope-discovery)); do not grow the design to fix the design.

Code placement and readability. For each nontrivial change, compare the chosen class and method with the existing owner of the behavior and relevant maintained code supplied in the packet. Check for duplicate rules, unnecessary indirection, unclear names, hard-to-follow control flow and departures from applicable project conventions. Point to the actual code and explain the maintenance or contract consequence. A style preference alone is advisory. If the supplied context is insufficient to judge material placement or compatibility, name the exact missing source in the coverage limits and use `unverified_material` for the affected material change. An optional style example is not a blocker.

Material decisions. Inspect dependency manifests and deployment files in the actual diff, including new files. Compare new direct dependencies, material architecture or infrastructure changes, and changed shared or cross-service behavior against the plan and recorded owner decision. Approval is the owner's reply after seeing the plan naming the decision, or prior owner words covering the named or bounded choice. A general go-ahead plus an agent-written plan does not supply it. Check affected callers supplied in the packet and mark a material missing caller as `unverified_material`, naming the missing evidence. For a nonobvious public signature change, check for a one-line reason in the PR description or, before a PR exists, the proposal summary. The reason explains the caller's need. A missing rationale is advisory if necessity and compatibility are otherwise established.

Compare the migration itself with the declared effect. A new table or column needs owner authorization even when its declaration says `schema`. Check the recorded owner wording for the actual change.

Integration review. For a boundary mapping, inspect the actual producer and consumer contract, and maintained examples using it when example search was allowed. Check incompatible invented values or normalization at the wrong end of the flow. For integration removals, verify the supplied search evidence and remaining references in source, settings across environments, deployment and docs. Point to obsolete references the task owns and preserve live shared configuration. Name material missing evidence through the coverage fields. Compare real source output with the agreed contract before accepting a downstream conversion. For broad downstream impact or credible reliance on old output, verify that the owner decided on the compatibility approach.

Proportionality is blocking. Sketch the minimal solution from the ticket, then compare the diff with the ticket and that sketch using [solution design](../task-orchestrator/references/solution-design.md) and its [calibration examples](../task-orchestrator/references/solution-calibration.md). Flag each mechanism that neither the ticket/acceptance nor a category (a) risk of [solution design](../task-orchestrator/references/solution-design.md#2-triage-every-risk-only-required-risks-become-code) requires (locks, transactions, claims, retries, queues, caches, polling, new IDs/columns/migrations, optional DI dependencies, re-checks of guaranteed state), shared/cross-cutting edits, bundled unrelated changes, tests for risks without a category (a) counterexample, a consumer-side workaround for a fixable source, and infrastructure added without the owner's approval. "More robust" is not a justification without a requirement; a category (a) mechanism names its concrete counterexample. Each is P2, P1 when it changes shared infrastructure or other tenants. Hunks that apply the same confirmed root-cause fix at other entry points, or remove its compensations, belong to that defect. For each infrastructure effect, check that the cited owner decision or source names that infrastructure; under an owner pre-approval accept only prepared files (and an apply in a dev environment the owner allowed), nothing beyond. An unapproved material decision, risky or complex refactoring absent from the approved plan, or out-of-scope refactoring is a finding (P2 by default). Low- or medium-risk refactoring in the task's code or tested flows belongs to the task. A diff far beyond the sketch triggers scrutiny; the finding names the specific hunks. A proportional change gets no invented findings.

Domain values. In production code the diff adds, list every conversion of a domain value (date or code formats, units, encodings, numbers or keys of an external system) and every literal that stands for such a rule (for example `99999999` for an inverted date, a custom format string), and search the repository for that literal, format and domain. Test data and expected values, identity values (0, 1, -1), protocol status codes and standard formats used through the standard library need no entry. Give each listed item one decision in the review, even without a finding: existing helper or constant used; belongs in the existing helper class of its domain as a method or named constant; or a named constant with a reason. P2: re-implementing an existing helper or constant; the same conversion, its inverse or the same literal inlined more than once; or any inline conversion where the repository has a helper class for that domain. P3: a single unexplained literal where no helper class for the domain exists. Each finding names the fix (the method or constant and the class it goes into). Correct results do not exempt the code, and checking only for duplicates of existing helpers misses a conversion no helper has yet.

Read `_ase_context/changed_files.json` when present: it states the owner-approved mode and, per changed file, whether you got the full body, a diff with context under `_ase_diff/` (code outside the context was not supplied: name judgments that need it as limits), or another review part's coverage (not your gap). `_ase_check_inputs/` holds read-only private check scripts the evidence commands ran; judge what they verify, never treat them as part of the change. Read `_ase_context/change_impact.json` when present: check each listed caller of a changed module against the changed contract (signature, return value, side effects). Callers are listed once in `caller_paths` and named by index per change; use the bounded `excerpts` for callers outside the packet, `excerpt_omitted` says why one has none, and `callers_not_listed` counts further matching callers that were not listed at all (a stated coverage limit). In a review part the index covers only that part's files. What the excerpts do not show is a stated limit, not an assumed pass. When the change touches authentication/authorization, untrusted input, secrets, permissions, command/file execution or outbound calls, check the relevant STRIDE threats (spoofing, tampering, repudiation, information disclosure, denial of service, elevation of privilege) and name the ones you ruled out.

For software examine correctness, missing requirements, errors, concurrency, security, compatibility, data integrity and meaningful tests. For .NET include DI lifetimes, CancellationToken propagation, EF queries/transactions, disposal, serialization and event idempotency. For other profiles use task-orchestrator's [profile evidence](../task-orchestrator/references/profile-evidence.md) and review the artifact, claims or actual resource postconditions; code-only checks do not replace that review.

Return each finding with severity, precise file/line or artifact locator, evidence, consequence and actionable fix guidance (separate `evidence`, `consequence`, `fix` fields when the schema has them; then also fill `inspected`, `limits`, and `unverified_material` for each material change whose necessity or correctness the supplied evidence does not let you establish, which blocks until context is supplied; do not use it for doubts you can resolve from the packet). P0/P1/P2 block approval; P3 is advisory. State what was inspected and the limits, even when there are no findings. Name the exact commit or artifact version reviewed, or the most precise available locator. Never return a bare OK: name material checks not exercised and substitutes (mocked provider/auth, fixture, synthetic data) that limit what the evidence establishes. A review of a change you implemented or co-authored in the same session (giving review findings is not co-authoring) is a self-check: label it "self-check, not independent" and do not report approval.

When the handoff supplies a finding journal, check the original exposed behavior against the current correction and executed proof. Supply explicit follow-up for each open finding in your scope and cite the current packet path and concrete evidence for a fix or disproof. Preserve the prior ID when a still-current defect moves or changes wording. A resolved entry or owner disposition stays in history. Report a recurrence when current evidence establishes it.

Use authorized local `ase` independent-session adapters for genuine runner receipts. Fixtures and descriptors prove only their protocol/structure. Blocking findings require in-scope repair, fresh checks and new independent AC/review against changed source. Preserve persisted root/stage budgets and authorization; unresolved infrastructure or scope blockers stop automatic mutation.
