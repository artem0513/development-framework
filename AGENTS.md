This repository implements Autonomous SE. Read docs/ADR-001.md for the trust boundary and docs/research.md for selected upstream components.

Use Python 3.11+ standard library for the runtime. While iterating, run the affected suites: `python -B -m ase.modules --affected <changed files> --test`. Run the full `python -m unittest discover -s tests -v` (about 30-40 minutes; on Windows under `powershell -ExecutionPolicy Bypass`) before pushing substantive runtime changes, and not while files are still being edited. Keep independent AC and review sessions separate from implementation; a deterministic adapter is only a protocol test, never independent semantic validation.

Treat this tool as a local reliability layer. Only a trusted CI runner plus server-side branch protection can enforce publishing against a hostile same-user agent. Reports must distinguish executed tests, independent judgments and unavailable enforcement.

This workspace explicitly adopts DevelopmentFramework for managed tasks. Use .agents/skills/task-orchestrator/SKILL.md and the appropriate domain skills. Choose software only for actual code or configuration implementation; documents, financial analysis, research and infrastructure use their own acceptance profiles. Preserve project rules and user authorization. Restore local context, propose the outcome concisely, and reuse an approved implementation plan for the same scope. Before asking about a missing fact, inspect supplied context and relevant authorized sources or environment with safe read-only checks. Keep the original chat as lead, process its durable ase events inbox and return results through available native tools. For software, plan relevant risk scenarios and require current independent test adequacy alongside acceptance/review. Distinguish retrievable facts from owner-only decisions; ask only for a material remaining gap, with checked evidence and a concise hypothesis/recommendation. When you investigate a fault or recommend a fix, also as a subagent or for a quick fix: read how the callee/source already handles the same condition (sibling paths, fallbacks) and recommend fixing it there; treat a lead's suggested fix as a hypothesis. No consumer-side retry, wait, timeout or compensation as the fix for a source fault while the source can be fixed, unless a requirement or documented contract prescribes it. Hold a patch that depends on an unresolved owner decision. If a new error can occur after a write commits, check what persisted and what retry does. A similar call elsewhere does not authorize a new failure in this flow. Unless this flow has an agreed failure policy, give the owner the options and hold the dependent diff. An inaccessible source does not justify guessing a correction to money, permissions or stored data. If two interpretations fit the same input, show that input and its different outcomes, then get the fallback approved. Verify deployment and retries before claiming single execution. A schedule or one replica setting alone cannot rule out repeats or overlap. A defect outside the ticket that this change did not cause is reported in one line asking whether it is needed at all; without the owner's explicit permission for that defect it is never fixed, committed, given the ticket key or put in any branch or PR, current or separate. If it blocks a check of a denial goal and a working control refuses with a 4xx (never 5xx, timeout or empty 200), judge the goal while still testing the task's own code; otherwise it is a blocker for the owner. An exact status code counts when it is itself the requirement. Each new domain conversion or magic value (date/code formats, units, external-system numbers or keys) uses an existing helper or constant, goes into the existing helper class of its domain, or becomes a named constant with a reason; self-checks, reviews and cleanup passes check every one, not only duplicates. When asked whether something exists, search first and answer with the fact. Independent acceptance and review plus the evidence gate are required for verified completion.
